# P1-09 — Graceful shutdown

- **Phase:** 1 — Instrumentation & health
- **Depends on:** P1-02 (flush hooks), P1-05 (HealthCheckService `stop()` in the sequence), P1-06 (RetentionService `stop()` in the sequence)
- **Blocks:** — (independent; do last in Phase 1 so flush targets exist)
- **Estimate:** 0.5 dev-day

## Objective

Today there are **no `SIGTERM`/`SIGINT` handlers** — a `docker compose stop` or k8s rolling deploy kills active WebSocket/voice conversations mid-sentence and loses buffered monitoring data. Add an orderly shutdown sequence.

## Scope

### New files
- `src/utils/shutdown.ts` — `installShutdownHandlers(deps)` (keeps `src/index.ts` thin)

### Modified files
- `src/index.ts` — install handlers after `startServer` (which must return the http `Server`, today `Promise<void>`)
- **All eight background services** — **verified: all eight already expose a public `stop(): void`** (the six below + `HealthCheckService` + `RetentionService` from P1-06): `ConversationTimeoutService`, `ScenarioRunExecutorService` in `src/services/testing/`, `BenchmarkExecutorService`, `ImapInboundService`, `OAuth2TokenRefreshService`, `ProcessingDeferralService`, `HealthCheckService`, `RetentionService` — nothing to add, just call them in the shutdown sequence (see soundness finding 1 — the original "six" wording missed `RetentionService`, added by P1-06 after this spec was drafted)
- `src/db/index.ts` — new idempotent `endPool()` export (the lazy `_pool`/`_db` refs are nulled so `getDb()` cannot resurrect the pool mid-shutdown; tests keep using `getPoolRef()`)
- `src/channels/websocket/WebSocketChannelHost.ts` — extend the existing `close()` (today it only closes the WSS server) to also explicitly close each tracked active socket with code 1001 "going away" before closing the server; add `getOpenSocketCount()` + `terminateOpenSockets()` for the drain loop
- `src/channels/twilio-voice/TwilioVoiceChannelHost.ts` — **new** `streamSockets` registry (the host tracks nothing today — `handleStreamConnection` is closure-scoped and there is no `close()` method; soundness finding 2) + `close()` closing active media-stream sockets with 1001 + cancelling `pendingOutboundCalls` bookkeeping + `getOpenSocketCount()`/`terminateOpenSockets()`

## Implementation requirements

Sequence on first `SIGTERM`/`SIGINT` (idempotent — second signal forces `process.exit(1)`):

1. Log `shutting down` (info) with signal name.
2. Stop the seven background services (`stop()` each) — no new work starts.
3. Stop `HealthCheckService` loop (eighth; kept as its own step so the sequence reads as spec'd).
4. Stop accepting new HTTP connections (`server.close()` + `closeIdleConnections()`, **not yet awaited** — Node fires the `close` callback only when *all* connections are done, including upgraded WS sockets, so awaiting first would deadlock behind the drain) — in-flight requests finish.
5. **Drain**: close WebSocket + Twilio voice connections with 1001 "going away", giving close handshakes + server-side session cleanup up to `SHUTDOWN_GRACE_MS` (env, default 10000, polling every 100 ms); then force-terminate (`ws.terminate()`) the remainder (pino warn with count), then await the `server.close()` callback. (Drain semantics vs "finish their current turn" — soundness finding 3.)
6. **Flush** (per logger): `await flushNow()` → `stop()` (no new interval/threshold flushes can start) → `await settled()` (wait for a concurrent in-flight flush so its insert cannot race the pool close) → `await flushNow()` again (drains records made while the first insert was running). Each bounded 5 s, timeout continues the shutdown. Then log the remaining `CallLogger.pendingCount` / `MetricsRegistry.pendingRowCount()` (flush re-queues on DB failure — don't claim "0 pending" blindly).
7. Close the pg pool (`endPool()` from `src/db/index.ts`).
8. `process.exit(0)` (explicit — also kills WebRTC sessions left behind, finding 4).

Hard outer timeout: 30 s from signal to `process.exit(1)` regardless of where it's stuck (timer set at signal receipt, cleared on clean exit).

## Acceptance criteria

- [x] `docker compose stop backend` (or `kill -TERM <pid>`) produces the ordered log lines: services stopped → connections closed → buffers flushed (0 pending) → pool closed → exit 0, with total time < `SHUTDOWN_GRACE_MS` + 5 s when idle. — Real-wiring smoke (SIGTERM via `process.kill`, unreachable-DB boot so flush paths were exercised): `Shutting down` → 8 × `… stopped` → `Shutdown: closing interactive connections (1001 going away)` → `WebSocket server closed` → `TwilioVoice: Media Streams WebSocket server closed` → `CallLogger stopped` → `MetricsRegistry stopped` → `Shutdown: monitoring buffers flushed` → `Database pool closed` → `Shutdown complete`, exit 0. Idle sequence took ~2 ms (well under `SHUTDOWN_GRACE_MS` + 5 s). `docker compose stop` sends the same SIGTERM.
- [x] An active WebSocket conversation at signal time is closed with 1001 and its in-flight turn completes or is force-closed at the grace deadline — no dangling `pg` handles, no hung process (verified in a manual smoke test, documented in PR description). — Host `close()` methods close every tracked socket with 1001 (WS + Twilio voice media streams); the 1001 close fires the normal `close` → `handleDisconnect` → `runner.cleanup()` path (the same disconnect path the existing WS e2e coverage exercises), aborting in-flight turns early. Grace-deadline force-terminate (`terminateOpenSockets()`) is covered by unit tests with stubbed hosts (2 WS + 1 voice sockets that never close → both `terminate` calls fire after the grace window, then exit 0). No-hang/no-dangling-handles verified in the smoke (exit 0, no hard-timeout line).
- [x] Second signal during shutdown exits 1 immediately. — Unit test: first shutdown hung in `endPool`, second `SIGTERM` → `process.exit(1)` recorded synchronously.
- [x] No effect on normal startup or the e2e suite (handlers installed only in `src/index.ts`, not in `createApp()` — tests don't trigger them). — `installShutdownHandlers` is called only in `src/index.ts` (finding 7); full gates after P1-09: `npm run build` 0, `npm run test:unit` 621 passing (613 + 8 new), `npm run test:e2e` 969 passing, `npm run test:integration` 35 passing.

## Tests

- **Unit** (`tests/unit/monitoring/p1-09-shutdown.test.ts`, 8 tests): ordered sequence + exit 0 with exact call-order assertion (incl. flush/stop/settled/final-flush); second signal → exit 1 while shutdown is in flight; hard timeout → exit 1 when a step hangs (stubbed `server.close` callback never fires); grace deadline force-terminates stuck sockets then exits 0; a throwing service `stop()` does not abort the sequence; a concurrent in-flight flush settles before `endPool` (finding 15); idle shutdown skips the grace wait; `uninstall()` removes the signal handlers.
- **Manual smoke (recorded in PR):** boot the real app (`startServer` + the exact `installShutdownHandlers` wiring from `src/index.ts`, unreachable DB so the flush-failure path is exercised) → `process.kill(pid, 'SIGTERM')` → assert the ordered log lines above + exit 0 + `Shutdown complete`.

## Out of scope

- PreStop hooks / k8s manifests (deploy concern), draining the DB pool of idle-only connections before step 4 (unnecessary), in-flight Twilio call teardown via Twilio API (best-effort local close is enough; the call simply ends).

## Soundness review (2026-08-17)

Findings from verifying this spec against the codebase before implementation (reconciled into the spec above):

1. **The stop list is seven background services + HealthCheckService, not six.** `server.ts:408-418` starts ten things: `MetricsRegistry`/`CallLogger` (flush intervals — handled by the flush step, not the stop list), the six services named in the spec, **plus `HealthCheckService` and `RetentionService` (P1-06 — this spec's "six" predates P1-06's `start()`)**. Missing `RetentionService.stop()` would leave two node-cron tasks alive → the process would never exit cleanly and every shutdown would hit the 30 s hard timeout → `exit(1)`. All eight `stop()` methods verified present (several already carry "P1-09 shutdown hook" comments from their own specs).
2. **`TwilioVoiceChannelHost` has no `close()` and no socket registry.** `handleStreamConnection(ws, req)` is fully closure-scoped (session, mark callbacks, instrumentation state all local) and the host exposes no `close()`/`stop()` — the spec's "close active media-stream connections" assumed tracking that doesn't exist. Fix: add `streamSockets: Set<WebSocket>` (registered after the rate-limit check, removed on `close`), plus a new `close()` (1001 each + `wss.close()` + clear `pendingOutboundCalls` with a warn log) and the drain accessors. `WebSocketChannelHost` by contrast already tracks `socketMap: Map<WebSocket, Session>` — its `close()` just needs the 1001 pass. (Note: `socketMap`/`sessionMap` are never pruned on disconnect — pre-existing slow leak, out of scope; the drain counts by `readyState`, so stale entries are harmless.)
3. **"Finish their current turn" is not mechanically observable — drain is close + cleanup window, not turn completion.** Closing a socket fires `handleDisconnect` → `SessionManager.unregisterSession` → `runner.cleanup()`, which **aborts** the in-flight turn (destroys converters/VAD, calls provider `cleanup()`) — it does not let it finish. There is also no turn-in-progress flag anywhere (`session.runner` is set for the conversation's whole lifetime), so "wait for the turn to end before closing" is undecidable. Implemented semantics: close everything with 1001 immediately, use the grace window to let close handshakes + the `cleanup()` chain finish (in-flight turns are aborted promptly — strictly better than waiting for the deadline), force-terminate stragglers. The acceptance criterion still holds: a quiescent turn (waiting for user input) "completes" trivially; an in-flight turn is force-closed (early, by cleanup) — and the 30 s hard timeout backstops anything stuck.
4. **WebRTC sessions are force-killed, not drained.** `WebRTCChannelHost` has no `initialize(server)` — its control channels ride on browser-initiated RTCPeerConnections, not the HTTP server. An active call's 10 ms audio-scheduler interval (ref'd) would otherwise keep the event loop alive; the explicit final `process.exit(0)` handles it. Consistent with the spec's out-of-scope stance on Twilio API teardown (the call simply ends). If graceful WebRTC close ever matters, it slots into the drain list.
5. **`server.close()` callback waits for *all* connections, including upgraded WS sockets** — so step 4 cannot be awaited before the drain (deadlock: the callback fires only after the very sockets the drain closes). Sequence: `server.close()` + `closeIdleConnections()` (releases idle keep-alive immediately) → drain → `await` the close callback → flush → pool → exit. A stuck (non-idle, non-WS) connection blocks the callback → hard timeout → `exit(1)`, the documented backstop.
6. **`startServer` must return the http `Server`** (today `Promise<void>`; the server is local). Only caller is `src/index.ts` — safe signature change. Tests never call `startServer` (they use `createApp()`), so the e2e suite is untouched.
7. **Handlers install only in `src/index.ts`**, not `createApp()`/`startServer()` — acceptance criterion 4 (e2e unaffected) falls out by construction.
8. **Flush re-queues on DB failure** — `CallLogger.flushNow()` re-queues failed rows ahead of newer ones, so "0 pending" after the final flush is only true when the DB accepts. The shutdown logs the real remaining `CallLogger.pendingCount` (new getter) instead of a fixed claim; `MetricsRegistry` gets a matching `pendingRowCount()` (counts unflushed counter/gauge/histogram deltas) for the same log line.
9. **No other ref'd handles keep the process alive** — audited: `IpRateLimiter.pruneTimer` is `.unref()`'d; `SmtpImapOAuth2Controller`'s TTL interval is `.unref()`'d; `WebRTCConnection.schedulerInterval` is cleared on connection close (and killed by `exit(0)` otherwise); all eight cron/interval loops are cleared by their `stop()`; pg pool by `endPool()`; sockets by the drain. With all of that done, the only reason the process would survive past the sequence is a stuck await → hard timeout.
10. **Testability** — `installShutdownHandlers(deps)` takes a structural `ShutdownDeps` (server, named services, two channel hosts, call logger, metrics registry, `endPool`, optional `graceMs`/`hardTimeoutMs` overrides) and returns an `uninstall()` closure; unit tests drive it with stubs via `process.emit('SIGTERM')` and a patched `process.exit`. The real wiring (container resolves, env `SHUTDOWN_GRACE_MS`) lives in `src/index.ts` and is covered by the manual smoke.

## Implementation (2026-08-18)

Files:

- `src/utils/shutdown.ts` (new) — `installShutdownHandlers(deps: ShutdownDeps): () => void`: idempotent `SIGTERM`/`SIGINT` handler (second signal → immediate `exit(1)`), the 8-step sequence (named service stops → `server.close()` + `closeIdleConnections()` not yet awaited → 1001 close of WS + voice sockets → grace drain polling every 100 ms with force-terminate at the deadline → await the `server.close()` callback → per-logger flush/stop/settled/final-flush (finding 15) → honest remaining-pending log → `endPool()` → `exit(0)`), a hard timeout set at signal receipt (default 30 s, cleared on clean exit, also cleared by `uninstall()`), per-step error containment (a throwing `stop()` is logged and the sequence continues; an unexpected error → `exit(1)`).
- `src/index.ts` — `startServer` result kept as `server`; `installShutdownHandlers` wired with the real container singletons (8 named services, `WebSocketChannelHost`, `TwilioVoiceChannelHost`, `CallLogger`, `MetricsRegistry`, `endPool`) and `graceMs` from `SHUTDOWN_GRACE_MS` (default 10 000).
- `src/server.ts` — `startServer` now returns `Promise<Server>` (was `Promise<void>`; finding 6). Only caller is `src/index.ts`; tests use `createApp()` and are untouched.
- `src/db/index.ts` — idempotent `endPool()`: nulls the lazy `_pool`/`_db` refs (so `getDb()` cannot resurrect the pool mid-shutdown), awaits `pool.end()`, logs `Database pool closed`; no-op when the pool was never initialized (unit/e2e worlds without a live pool stay safe).
- `src/channels/websocket/WebSocketChannelHost.ts` — `close()` now closes every socket in `socketMap` with 1001 "going away" before closing the WSS server; new `getOpenSocketCount()` (counts by `readyState` — stale map entries are harmless) and `terminateOpenSockets()` (returns the count terminated).
- `src/channels/twilio-voice/TwilioVoiceChannelHost.ts` — new `streamSockets: Set<WebSocket>` registry (added after the rate-limit check in `handleStreamConnection`, removed on `close`); new `close()` (1001 each + WSS close + `pendingOutboundCalls.clear()` with a warn log when non-empty); `getOpenSocketCount()`/`terminateOpenSockets()` for the drain.
- `src/services/monitoring/CallLogger.ts` — new `pendingCount` getter (buffer length) for the honest shutdown log; `flushInFlight` tracking + `settled()` + a `stopped` flag gating the threshold trigger after `stop()` (finding 15).
- `src/services/monitoring/MetricsRegistry.ts` — new `pendingRowCount()` (unflushed counter/gauge/histogram delta entries) for the same log line; `flushInFlight` tracking + `settled()` (finding 15).
- `src/services/BenchmarkExecutorService.ts` — `start()`: `resetStuckRuns()` now has a `.catch()` (heartbeat error + log) before `.then(() => this.checkAndProcess())` — pre-existing unhandled-rejection crash found by the smoke test when the DB is down at startup (finding 11).
- `tests/unit/monitoring/p1-09-shutdown.test.ts` (new, 8 tests — see Tests above).

Implementation findings (pitfalls hit and fixed during implementation):

11. **`BenchmarkExecutorService.start()` had an unhandled rejection at startup.** `this.resetStuckRuns().then(() => this.checkAndProcess())` — `resetStuckRuns()` is the only awaited-DB call in any `start()` without a `.catch()` (all others use `.catch()` or are cron/interval-based, which contain their own rejections). With an unreachable DB the rejection is unhandled and Node 24 aborts the process (exit 7, `process.abort`) before the server even listens — the smoke test found this on first run. Fixed with a `.catch()` that records a heartbeat error, logs, and still proceeds to `checkAndProcess()` (which contains its own rejections). In production the `index.ts` `SELECT 1` preflight makes this a narrow window (DB dies between preflight and service start), but a crash-loop on deploy is exactly what P1-09 exists to prevent.
12. **The hard timeout must be cleared by `uninstall()`.** The timer is set at signal receipt and is independent of the signal listeners. A shutdown left in flight (the unit tests' `endPool`-hang scenario) otherwise leaves a 60 s timer that fires later against a *restored* `process.exit` and kills the surrounding process (observed: the unit runner died 60 s after the suite ended with `hard timeout exceeded — forcing exit`). `uninstall()` now clears it; the clean path still clears it before `exit(0)`/`exit(1)`.
13. **Unit-test `process.exit` patches must return, not throw.** A throwing sentinel re-enters `runShutdown`'s `catch` → second `process.exit(1)` → unhandled rejection in the `void runShutdown()` promise → Node 24 aborts the test process. The patch records the code and returns normally, so `runShutdown` finishes cleanly after the recorded exit.
14. **Smoke evidence (real wiring, unreachable DB):** full ordered log sequence in ~2 ms, exit 0. The flush step against a down DB behaved exactly as designed: `MetricsRegistry flush to metric_samples failed — deltas kept in memory`, then `Shutdown: monitoring buffers flushed` honestly reporting `callLogPending: 0, metricSamplesPending: 5` (finding 8 — the fixed "0 pending" claim would have been a lie here), and the sequence still completed to `exit(0)`.
15. **In-flight flush vs `endPool` race (found in post-implementation race review).** Both `flushNow()` implementations guard with `if (this.flushing) return;` — but if an interval-triggered flush (5 s / 60 s) or a CallLogger 200-row threshold flush is *running* at shutdown time, the shutdown's `await flushNow()` **no-ops through the guard** while that insert is still in flight; the sequence then proceeded to `endPool()`, which can close the pool underneath the running insert → "Pool is closing" → rows re-queued / deltas kept → silently lost at `exit(0)` plus a confusing error at the worst moment. Fix: each class tracks `flushInFlight` and exposes `settled(): Promise<void>`; the shutdown flush step became initial drain → `stop()` → `await settled()` → final drain, per logger (step 6 above), and `CallLogger.record()`'s threshold trigger is gated by the `stopped` flag so no new flush can start between the final drain and `endPool()`. Records still made by in-flight *background work* (scenario/benchmark runs keep running after their `stop()` clears only the timers) after the final drain are accepted as lost and are visible in the honest pending log — waiting for unbounded long-running work is exactly what the 30 s hard timeout is for.
16. **Race review — checked, safe without changes:** (a) double signal — `onSignal` is fully synchronous to `shuttingDown = true`; single-threaded Node cannot interleave two handlers. (b) hard timer vs clean exit — after the last `await` (endPool) the clean path runs to `clearTimeout` + `exit(0)` in one microtask chain, which preempts the timer macrotask; the timer can only win while an await is still pending (the intended backstop). (c) WS upgrades on existing keep-alive connections after `server.close()` — impossible once the host `close()`s run: `wss.close()` removes the HTTP `upgrade` listener, and each keep-alive connection is either in-flight (cannot send another request) or idle (released by `closeIdleConnections()`; Node's 5 s keep-alive timeout reaps the rest). (d) `server.close()` callback vs stuck non-WS connection — documented backstop: hard timeout → `exit(1)`. (e) in-flight background work vs `endPool` — `pool.end()` waits for checked-out clients; brief queries finish and return clients; a 30 s+ query hits the hard timeout. Benchmark runs self-heal on next start (`resetStuckRuns()`); **scenario runs have no equivalent startup reset** — a force-killed run can stay in a non-terminal status (pre-existing gap, same after `kill -9`; recommend mirroring `resetStuckRuns()` for scenario runs as a follow-up). (f) drain/terminate double-close — counts are `readyState`-based (OPEN or CLOSING); `terminate()` on a CLOSING socket safely force-completes it.
