# P1-04 — Request-outcome logging, requestId, API request metrics, pino redaction

- **Phase:** 1 — Instrumentation & health
- **Depends on:** P1-02
- **Blocks:** P2-01 (5xx/429 rules consume `api_requests_total`)
- **Estimate:** 0.5 dev-day

## Objective

Make API traffic observable: every request gets a `requestId`, an outcome log line (status, duration, operator), request metrics, and secrets stop appearing in logs.

## Scope

### New files
- `src/http/middleware/requestOutcome.ts`

### Modified files
- `src/server.ts` — register middleware (after the `/health` route, before the incoming-request log line so that line can carry `requestId`; still before the rate limiter so limiter rejections are also counted) + `requestId` on the incoming-request log line
- `src/utils/logger.ts` — add `redact: { paths: ['req.headers.authorization', 'res.headers.authorization'], censor: '[REDACTED]' }`, exported as `LOG_REDACT` (test seam: a unit test builds a pino instance from the exact config and asserts on captured output)
- `src/http/middleware/requestContext.ts` — `requestId` reuses `req.id` (falls back to generating its own only if `req.id` is absent, e.g. middleware order changes) so context, outcome log and response header never diverge
- `src/http/middleware/errorHandler.ts` — include `req.id` in the unhandled-error log line
- `src/services/monitoring/MetricsRegistry.ts` — raise `routeGroupCap` 100 → 200 (see finding 4)
- `tests/setup.ts` — expose the app-world `MetricsRegistry` as `globalThis.__TEST_METRICS_REGISTRY__` (see finding 10)
- `tests/unit/monitoring/metricsRegistry.test.ts` — the `route_group` cap test updated 100 → 200 (with the 152-pattern rationale)

## Implementation requirements

1. **requestId**: generate uuid at the start of the request (honor an inbound `X-Request-Id` header if present), store on `req.id`, echo it in the `X-Request-Id` response header.
2. **Outcome log** on `res.on('finish')`: `{ requestId, method, route, status, durationMs, operatorId? }` — level: `error` for 5xx (with route + status), `warn` for 4xx, `debug` for 2xx/3xx (keeps stdout clean; incoming-request log line at info stays as-is and gains `requestId`).
3. **Metrics** via `MetricsRegistry`:
   - `api_requests_total{method, route_group, status_class}` — `route_group` = normalized express route pattern (e.g. `/api/conversations/:id`) falling back to first two path segments to keep cardinality bounded; `status_class` = `2xx|3xx|4xx|5xx`.
   - `api_request_duration_ms{method, route_group}` histogram.
4. **Skip** `/health` (registered before this middleware anyway) and `/metrics` (Phase 4, P4-01 — skipped by an explicit path check so the requirement holds even before P4-01 lands) — no metrics or logs for probe/scrape traffic. (There is no `/health/ready` endpoint — only `/health`; the original spec's mention of `/health/ready` was removed.)
5. **Pino redaction** of `Authorization` (request + response headers) in all log lines.

## Acceptance criteria (verified 2026-08-17)

- [x] Every API response carries `X-Request-Id`; log lines for the same request share it (incoming + outcome + errors). — e2e: header present on 200 (unique per request) and 404, inbound header echoed unchanged; `requestContextMiddleware` reuses `req.id` for `context.requestId`; errorHandler logs `req.id`.
- [x] 5xx responses produce an `error`-level outcome line; `api_requests_total` and duration histogram increments verifiable via `MetricsRegistry.snapshot()` in tests. — unit: 5xx through the real middleware with a capturing registry (counter + histogram, `status_class=5xx`), 2xx path likewise; e2e: 2xx/4xx series + histogram visible in the app-world registry snapshot.
- [x] No `Bearer ...` token appears anywhere in logged output (add a unit/e2e assertion that greps captured logs for a known test token). — unit: pino instance built from the exported `LOG_REDACT` censors `req.headers.authorization` / `res.headers.authorization` to `[REDACTED]`; the raw token never appears in captured output.
- [x] Full e2e suite green (936 passing including the 4 new tests; 932 before this issue).

## Soundness review (pre-implementation, 2026-08-17)

1. **Registration order corrected.** The original placement ("after `requestContextMiddleware`") contradicts requirement 2: the incoming-request log line (`server.ts`, registered right after `/health`) runs *before* `requestContextMiddleware`, so it cannot carry a `requestId` generated by a later middleware. The middleware is registered right after the `/health` route, before the incoming-request log line — the stated rationale ("before the rate limiter so limiter rejections are also counted") still holds, and `durationMs` now covers the whole request including auth middleware time.
2. **`/health/ready` does not exist** — only `GET /health` is registered. Skip list reduced to `/health` + `/metrics`.
3. **`req.context.requestId` divergence.** `requestContextMiddleware` generates its own `generateId(ID_PREFIXES.REQUEST)` for authenticated requests only. Left alone, context logs and the outcome/`X-Request-Id` value would carry two different IDs. Fix: `requestId: req.id ?? generateId(...)`.
4. **`route_group` cap was too low.** The app registers **152 distinct route patterns** (244 route registrations) across 43 controllers, and the P1-02 `routeGroupCap` was `max: 100` with first-come-first-served overflow to `other` — ~50 real routes would have been permanently bucketed. Cap raised to 200 (still bounded; `maxSeries: 4000` remains the backstop).
5. **`route_group` resolution mechanics.** `req.route` is only populated after routing completes, so the pattern is resolved in the `res.on('finish')` handler: `req.baseUrl + req.route.path` when a route matched, otherwise the first two path segments of `req.path` (404s, and rate-limiter rejections that never reach a route — their `status_class=4xx` still identifies them; P1-07 carries limiter-specific detail).
6. **No stable 500 exists in the e2e environment** (the known agents tag-filter 500 is a test-env quirk deliberately excluded from the suite). The 5xx outcome level and metrics are therefore unit-tested deterministically (pure `resolveOutcomeLevel()` mapping table + fake `req`/`res` through the real middleware with a capturing `MetricsRegistry`); e2e covers 2xx/4xx series, header round-trip and `snapshot()` verification.
7. **Redaction testability.** The redact config is exported as `LOG_REDACT`; the unit test constructs a pino instance from that exact config with a memory stream and asserts a known test token never appears (it appears censored instead) — no logger-instance swapping needed.
8. **CORS preflights** are answered by the `cors` middleware (registered before this one) and never reach the outcome middleware — preflight responses carry no `X-Request-Id` and are not counted. Accepted: preflights are the least informative traffic to meter.
9. **Inbound `X-Request-Id` sanitization.** The inbound header is honored only if non-empty and ≤ 128 chars after trim; otherwise a house-style `req_<uuidv7>` ID (`generateId(ID_PREFIXES.REQUEST)`) is generated. Bounds header and log-line size against hostile clients.
10. **Dual module graph in e2e (verified during implementation).** E2E test files load in a *different* module graph from the app: the runner entry (`tsx tests/runner.ts`) imports `tests/setup.ts` → `src/server.ts` as ESM, while mocha loads test files through its tsx `require` hook (CJS). The tsyringe `container` is shared (it is a CJS package), but `src/**` classes are loaded twice, so `container.resolve(MetricsRegistry)` from a test file returns a **different singleton** than the one the app's middleware records into. Consequence: e2e assertions on in-memory metric state must read the instance exposed on `globalThis.__TEST_METRICS_REGISTRY__` by `tests/setup.ts` (which lives in the app's module graph), not resolve it from the test-side container. This quirk predates P1-04 — it is why the P1-03 unit tests register their fakes via `container.registerInstance` + `resetMonitoringAccessorsForTests()` instead.

## Tests

- **E2E** (`tests/e2e/request-outcome.test.ts`): request with `authed()` → `X-Request-Id` present, unique per request; inbound `X-Request-Id` echoed back; header present on 404 too; the app-world registry snapshot (via `globalThis.__TEST_METRICS_REGISTRY__`, see finding 10) shows the 2xx/4xx `api_requests_total` series and `api_request_duration_ms` observations. The 4xx series uses a multi-segment unmatched path (`/api/nothing/at-all` → `route_group=/api/nothing`) so the first-two-segments fallback is exercised.
- **Unit** (`tests/unit/monitoring/p1-04-request-outcome.test.ts`): `resolveOutcomeLevel()` mapping table (2xx/3xx → debug, 4xx → warn, 5xx → error); `resolveRouteGroup()` normalization table (matched route → `baseUrl + path`, unmatched → first two segments, single-segment and root paths); 5xx through the real middleware with fake `req`/`res` + capturing registry (counter + histogram increments, `status_class=5xx`); redaction via a pino instance built from `LOG_REDACT` with a captured stream (known token censored, never present).

## Out of scope

- Distributed tracing (no OpenTelemetry in this phase), per-operator quota accounting (that's the rate limiter's job, P1-07).
